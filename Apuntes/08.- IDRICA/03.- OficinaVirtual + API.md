# Low

**Session Token Exposed in URL (WordPress Logout Nonce)**

**CVSS v3.1:** `AV:N/AC:H/PR:N/UI:R/S:U/C:N/I:N/A:L` → 2.6 — Low / Bajo

_(Puntuación orientativa si se demuestra que la exposición del nonce permite provocar el cierre de sesión de otro usuario. Si únicamente se identifica el parámetro en una URL, sin impacto explotable demostrado, debería considerarse Informational.)_

**Threat**

EN: An attacker who obtains a URL containing a valid session-related token or security nonce may be able to retrieve it from browser history, web server logs, proxy logs, or through the HTTP Referer header when users navigate to external resources. Depending on the token's purpose and validity, this information could potentially be abused to perform unauthorized actions or interfere with an authenticated user's session.

ES: Un atacante que obtenga una URL que contenga un token relacionado con la sesión o un nonce de seguridad válido podría recuperarlo a través del historial del navegador, los registros del servidor web, los registros de los servidores proxy o mediante la cabecera HTTP Referer cuando los usuarios naveguen hacia recursos externos. Dependiendo de la finalidad y validez del token, esta información podría utilizarse potencialmente para realizar acciones no autorizadas o interferir con la sesión de un usuario autenticado.

**Description**

EN: The application exposes a WordPress security nonce (`_wpnonce`) within a URL associated with the logout functionality (`wp-login.php?action=logout`). The parameter is included in the URL returned in the application's HTTP response:

`https://ov-pentesting.go-aigua.com/es/wp-login.php?action=logout&_wpnonce=4cffc515c4`

Placing security-related tokens in URLs increases the risk of unintended disclosure, as URLs may be stored in browser history, web server logs, proxy logs, or transmitted through the HTTP Referer header. Although WordPress nonces are primarily designed to protect against Cross-Site Request Forgery (CSRF), their exposure outside their intended context may facilitate unintended actions, such as triggering a logout operation if the nonce remains valid and the victim's authenticated session is available.

ES: La aplicación expone un nonce de seguridad de WordPress (`_wpnonce`) dentro de una URL asociada a la funcionalidad de cierre de sesión (`wp-login.php?action=logout`). Este parámetro se incluye en una URL devuelta en la respuesta HTTP de la aplicación:

`https://ov-pentesting.go-aigua.com/es/wp-login.php?action=logout&_wpnonce=4cffc515c4`

La inclusión de tokens relacionados con la seguridad en las URL incrementa el riesgo de divulgación involuntaria, ya que estas pueden almacenarse en el historial del navegador, los registros del servidor web, los registros de los servidores proxy o transmitirse mediante la cabecera HTTP Referer. Aunque los nonces de WordPress están diseñados principalmente para proteger frente a ataques Cross-Site Request Forgery (CSRF), su exposición fuera del contexto previsto podría facilitar acciones no deseadas, como provocar el cierre de sesión de un usuario si el nonce sigue siendo válido y la sesión autenticada de la víctima está disponible.

**Recommendations**

EN: Avoid transmitting security tokens, session identifiers, or CSRF nonces through URL parameters. Whenever possible, use HTTP POST requests to transmit security-sensitive parameters within the request body. Additionally, review the WordPress logout implementation to ensure that nonces are handled securely, configure an appropriate `Referrer-Policy` header (such as `strict-origin-when-cross-origin` or `no-referrer`), and ensure that sensitive values are not unnecessarily exposed in application logs or browser-accessible URLs.

ES: Evitar transmitir tokens de seguridad, identificadores de sesión o nonces CSRF mediante parámetros en las URL. Siempre que sea posible, utilizar peticiones HTTP POST para transmitir parámetros sensibles dentro del cuerpo de la solicitud. Adicionalmente, revisar la implementación del cierre de sesión de WordPress para garantizar que los nonces se gestionan de forma segura, configurar una cabecera `Referrer-Policy` adecuada (como `strict-origin-when-cross-origin` o `no-referrer`) y garantizar que los valores sensibles no queden expuestos innecesariamente en los registros de la aplicación o en URL accesibles desde el navegador.
